# Owner-record derivation for the ZH retrospective audits

This directory contains the selected release-disposition records used by the
three ZH audits. The provider's export workbook is identified by its SHA-256
below and is not included in this tree; the selector verifies the workbook
against the provider's own v23 manifest before selecting.

## Selection rules

1. Only the three audited releases are included: `R-FB-2026-07-8.9.3.6`,
   `R-FB-2026-08-8.9.3.6-P1`, `R-FB-2026-08-NORMAL-07` (31 rows).
2. Every other release is excluded, including `R-FB-2026-08-SCRIPT1`
   (labeled as scripted by the provider's own manifest).
3. The redundant `status` column is dropped; the provider's dictionary declares
   it equal to `disposition` in every row.
4. Role names are translated per the declared vocabulary in
   `scenarios/owner_records_select.py` to `Disposition Reviewer`,
   `Operations Executor`, and `Verification Officer`; every other field value
   is copied verbatim.

## Case construction rules

- **Raw arrivals.** One raw signal per distinct `signal_id`; later version rows
  are disposition records, not new signal arrivals. Payloads are verbatim
  selected rows (minus the internal source-row index).
- **Effective disposition.** For each signal, the latest non-provisional version
  (highest `version`) is effective. A signal with only a provisional record
  keeps zero effective dispositions, which the verifier reports as a missing
  effective disposition rather than inventing one.
- **Disposition mapping.** `admitted`, `rejected`, and `noncandidate` map to
  `RESOLVED`; `unresolved` maps to `UNRESOLVED`.
- **Gate construction (B0).** Each `approval` or `deployment` row yields one
  required gate. `disposition=admitted` maps to PASS; every other value maps to
  FAIL. These are constructed record gates, not a tool-native gate log; B0
  reviews the recorded rows and does not re-execute any gate.
- **Cutoffs.** Each audit's cutoff is a business moment in the records, frozen
  in `scenarios/build_case.py` `ZH_ANCHORS` with its basis. Times are local
  UTC+8 in the workbook and converted to UTC (owner receive convention +5s).
  R3 uses the record times 09:55:05 / 10:56; the task-book face 11:00 / 11:10
  is a declared anonymization-drift label, not the record time.
- **R4 identity conflict.** The selected ledger records `SIG-FB-260820-010` as
  a deployment on 2026-08-18 14:12 local. The derived R4 evidence copy records
  a change event for the same operation id on 2026-08-20 06:25Z (14:25 local).
  The provider's v23 manifest marks the id `EXCLUDED_AS_DUPLICATE_IDENTITY`
  with `EVIDENCE_IDENTITY_PENDING`. The ledger follows the producer's standing
  exclusion; the conflict is the subject of the audit.

## R4 evidence copy

`R4_EVIDENCE/` is generated by `scenarios/r4_evidence_select.py` from the
provider package's `R4_EVIDENCE/` directory. It removes exactly the two
export-metadata columns `data_usage_boundary` and `publication_clearance` and
copies every event field verbatim; `provenance.csv` records the original and
derived SHA-256 of each file. The provider package itself is never modified.
This copy is case-external record-review context, not an input to the B2
closure verdict.

## Not covered

The original R4 scenario text claimed "6/6 dispositions" and a snapshot that
"stays frozen". The shipped records contain no six-of-six disposition set and
no snapshot or frozen-state record. Both claims are marked `NOT_COVERED` in the
scenario catalog and are not asserted by any audit output.
